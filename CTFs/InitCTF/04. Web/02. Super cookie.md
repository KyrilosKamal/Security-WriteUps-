# Super Cookie

**Category:** Web  
**Points:** 100  
**Challenge ID:** 24

## Challenge brief

The challenge presents an office-story archive with an admin area. The hint indicates that the session cookie is insecure.

## 1. Discover the admin path

The site's `robots.txt` disclosed a non-obvious admin path:

```text
Disallow: /admin/8f14e45f-ea9d-4b21-9c6d-62f8f7a6c311
```

Visiting the path as a guest displayed the current session identity:

```text
You are currently browsing as: visitor
```

This was a clue to inspect how the application represented and validated the session.

## 2. Inspect the session cookie

The observed cookie had the structure of a signed Flask session value:

```text
payload.timestamp.signature
```

Example guest cookie from the lab:

```text
eyJyb2xlIjoiZ3Vlc3QiLCJ1c2VybmFtZSI6InZpc2l0b3IifQ.avhWcA.K_XIoCRq9uBhut4C3rGLyBY1iBY
```

The first component is Base64URL-encoded serialized session data. Decoding it reveals the guest role and username, but changing that data alone invalidates the signature.

Flask's default session mechanism uses itsdangerous signing. In the configuration inferred for this challenge, the relevant parameters were the `cookie-session` salt, HMAC key derivation, and SHA-1 digest. These details should be verified against the exact Flask/itsdangerous version and application configuration when assessing a real application.

## 3. Recover the weak signing secret

The challenge's weak signing secret was recovered offline using a wordlist. The recorded candidate was:

```text
secret123
```

A weak Flask `SECRET_KEY` allows an attacker who can reproduce the signing scheme to create a valid signature for modified session data. The secret should never be treated as a password that can safely be chosen from a small dictionary.

## 4. Forge the session data

The challenge accepted an admin session payload:

```json
{
  "role": "admin",
  "username": "admin"
}
```

The application checked the `role` value for `admin`. The string `administrator` did not satisfy that check in this challenge.

The forged cookie had the same general structure:

```text
<base64url-session-payload>.<timestamp>.<valid-signature>
```

The signature must be generated using the challenge's actual serializer settings and recovered secret. Merely editing the Base64URL payload is not sufficient.

## 5. Access the admin area

Submitting the correctly signed session cookie to the discovered admin path granted access to the challenge's admin page.

## Attack-chain summary

1. Read `robots.txt` and discover the hidden admin route.
2. Inspect the guest session cookie.
3. Identify the signed Flask session format.
4. Recover the weak signing secret offline.
5. Create a session payload with the admin role.
6. Sign the modified session using the challenge's serializer configuration.
7. Submit the forged cookie and access the admin area.

## Security impact and remediation

| Weakness | Impact | Remediation |
|---|---|---|
| Weak Flask `SECRET_KEY` | Attackers may forge valid session cookies | Generate a high-entropy random secret and store it securely |
| Authorization based on client-held session claims | A forged or incorrectly validated session can grant elevated access | Enforce authorization server-side and validate every privileged request |
| Admin route disclosed in `robots.txt` | Makes route discovery easier, but does not itself grant access | Do not rely on obscurity; protect the route with strong authentication and authorization |

## Takeaways

- Flask session cookies are signed, not encrypted by default; Base64URL decoding does not reveal a signing secret.
- A signature protects integrity only while the signing key remains secret and strong.
- Authorization must be enforced on the server for every privileged action.
- A path listed in `robots.txt` is not an access-control mechanism.
- When documenting a cookie-forgery lab, record the framework version and serializer settings so the signature analysis is reproducible.
